║   3. NLP SUGGESTION FLOWCHART   (CORE FEATURE)                           ║
╚══════════════════════════════════════════════════════════════════════════╝
  3a. The headline flow — what happens between one click and one screen:
  ┌────────────────────────────────────────────────────────────┐
  │ START                                                      │
  │ Client signed in as role "user" (protected /user subtree)  │
  └─────────────────────────────┬──────────────────────────────┘
                                │
                                ▼
  ┌────────────────────────────────────────────────────────────┐
  │ 1. User types the problem    /user/get-suggestions         │
  │ GetSuggestionsPage.tsx — free-text textarea, plus 5 sample │
  │ queries that fill the box on click                         │
  └─────────────────────────────┬──────────────────────────────┘
                                │
                                ▼
  ┌────────────────────────────────────────────────────────────┐
  │ 2. React sends the request                                 │
  │ analyzeLegalProblem(query, { onProgress }) — nlpService.ts │
  │ the onProgress events drive the AIProcessingModal stages   │
  └─────────────────────────────┬──────────────────────────────┘
                                │
                                ▼
  ┌────────────────────────────────────────────────────────────┐
  │ 3. MSW intercepts the call   (mock path)                   │
  │ POST /api/nlp/analyze → src/mocks/handlers/nlp.ts          │
  │ keyword match against the knowledge-base articles          │
  └─────────────────────────────┬──────────────────────────────┘
                                │
                                ▼
  ┌────────────────────────────────────────────────────────────┐
  │ 4. OpenRouter AI   (live path)                             │
  │ openrouter.ai/api/v1/chat/completions, called straight     │
  │ from the browser · legal-intake prompt                     │
  │ model chain: PRIMARY → FALLBACK → FAST                     │
  └─────────────────────────────┬──────────────────────────────┘
                                │
                                ▼
  ┌────────────────────────────────────────────────────────────┐
  │ 5. The AI returns JSON                                     │
  │ parseResponse.normalizeLegalAnalysis() validates the shape │
  │ confidence 0 + a non-legal case type = refusal, not advice │
  └─────────────────────────────┬──────────────────────────────┘
                                │
                                ▼
  ┌────────────────────────────────────────────────────────────┐
  │ 6. React displays the suggestions                          │
  │ /user/suggestions/results — SuggestionsResultsPage.tsx     │
  │ suggested case type, urgency, matched articles,            │
  │ recommended attorney, available slots                      │
  └─────────────────────────────┬──────────────────────────────┘
                                │
                                ▼
  ┌────────────────────────────────────────────────────────────┐
  │ END                                                        │
  │ the result stays in the Zustand store until you leave      │
  └────────────────────────────────────────────────────────────┘

  NOTE — the order of steps 3 and 4. The brief puts MSW before OpenRouter; the
  code does the opposite. analyzeLegalProblem() tries OPENROUTER FIRST and only
  replays the MSW endpoint when the live AI is missing, rate-limited, timed out
  or unparseable. The UI is honest about which one answered: every result carries
  a source of 'openrouter' | 'msw' | 'fallback', shown as a badge on the results
  page. The four levels are listed in 3b.

── 3b. WHAT THE SERVICE REALLY DOES ────────────────────────────────────────

  Four levels, always tried in this order (src/ai/services/nlpService.ts):
  ┌───────┬──────────────────────────────────┬──────────────────┐
  │ LEVEL │ WHAT IT DOES                     │ SPEED            │
  ├───────┼──────────────────────────────────┼──────────────────┤
  │ 1     │ cached result, same description  │ instant          │
  │ 2     │ OPENROUTER · legal-intake prompt │ a few seconds    │
  │ 3     │ MSW /api/nlp/analyze keyword hit │ instant, offline │
  │ 4     │ local keyword scan, no network   │ last resort      │
  └───────┴──────────────────────────────────┴──────────────────┘

  Progress stages the modal can show (AIProgressStage in src/ai/types/index.ts):
    preparing ▶ requesting ▶ retrying ▶ received ▶ parsing ▶ enriching ▶
    fallback ▶ done
  The countdown is real data: a rolling average of the last 8 runs, kept in
  localStorage under the key jurisflow.ai.intake.samples.

  Enrichment — after the model answers, still inside nlpService:
  ┌────────────────────────────────────┬──────────────────────────┐
  │ CALL                               │ RESULT                   │
  ├────────────────────────────────────┼──────────────────────────┤
  │ GET /api/knowledge/articles (MSW)  │ matched articles         │
  │ GET /api/availability (MSW)        │ attorney + slots         │
  └────────────────────────────────────┴──────────────────────────┘

  The object handed to the UI (frontend type NLPAnalysis):
    query · extractedKeywords · suggestedCaseType · confidence · matchedArticles
    recommendedAttorney { name, specialization, availableSlots }
    requiredServices · nextSteps   (+ urgency, source, model, keyFacts)

║   5. APPOINTMENT FLOWCHART                                               ║
╚══════════════════════════════════════════════════════════════════════════╝
  Attorney publishes the hours → client sees the free slots → client books →
  both sides see the confirmation.

  ┌────────────────────────────────────────────────────────────┐
  │ START   (the firm publishes when its attorneys are free)   │
  │ AvailabilityPage canEdit → /attorney/availability          │
  │ (the admin sees the same screen at /admin/availability)    │
  └─────────────────────────────┬──────────────────────────────┘
                                │
                                ▼
  ┌────────────────────────────────────────────────────────────┐
  │ STEP 1 — Attorney sets availability                        │
  │ day (Monday–Friday) + start time + end time + isAvailable  │
  │ POST /api/availability — MSW keeps it in memory            │
  │ PUT /api/availability/:id and DELETE edit or drop a slot   │
  └─────────────────────────────┬──────────────────────────────┘
                                │
                                ▼
  ┌────────────────────────────────────────────────────────────┐
  │ STEP 2 — User sees the slots                               │
  │ SuggestionsResultsPage card "Available Appointment Slots": │
  │ nlpService builds it from GET /api/availability, and falls │
  │ back to weekday 10:00 / 14:00 slots when it is empty       │
  │ and /user/appointments lists what is already booked        │
  └─────────────────────────────┬──────────────────────────────┘
                                │
                                ▼
  ┌────────────────────────────────────────────────────────────┐
  │ STEP 3 — User books a slot                                 │
  │ New Appointment modal: title, date, time, duration, type,  │
  │ notes, location → createAppointment() in appStores         │
  │ POST /api/appointments → the record is "scheduled"         │
  └─────────────────────────────┬──────────────────────────────┘
                                │
                                ▼
  ┌────────────────────────────────────────────────────────────┐
  │ STEP 4 — Confirmation                                      │
  │ the card appears under "Upcoming" (status scheduled)       │
  │ completed or cancelled rows drop into "Past" · admin,      │
  │ secretary and the client can delete from the card          │
  └─────────────────────────────┬──────────────────────────────┘
                                │
                                ▼
  ┌────────────────────────────────────────────────────────────┐
  │ END   (booked — nothing is stored outside the browser)     │
  └────────────────────────────────────────────────────────────┘

  WHO CAN DO WHAT
  ┌──────────────────────┬────────────────────────────────────────┐
  │ ROLE                 │ APPOINTMENTS                           │
  ├──────────────────────┼────────────────────────────────────────┤
  │ System Admin         │ all appointments · create + delete     │
  │ Attorney             │ own appointments · create + delete     │
  │ Legal Secretary      │ all appointments · create + delete     │
  │ Client (user)        │ own appointments · create + delete     │
  └──────────────────────┴────────────────────────────────────────┘

  NOTE — AppointmentsPage defaults canCreate and canDelete to true, and the
  admin and secretary routes pass them explicitly, so in this build every role
  that mounts the page (admin, attorney, secretary, client) can book and delete.
  The client sees a "Book" link on each suggested slot in
  SuggestionsResultsPage; that link is rendered but not wired to the create
  call, so booking is done from /user/appointments. Availability is an
  attorney/admin screen only: there is no /user/availability route.
  The secretary is the only role with the Calendar view (/secretary/calendar).

── 6a. LEGEND ──────────────────────────────────────────────────────────────

  ┌────────────────┬────────────────────────────────────────────┐
  │ SYMBOL         │ MEANING                                    │

── 6d. NOTES ───────────────────────────────────────────────────────────────

  (a) MSW vs OpenRouter. The brief order "React → MSW → OpenRouter" is not what
      the code does: the AI service calls OpenRouter first and uses the mocked
      /api/nlp/analyze endpoint only as the offline fallback (section 3b). App
      data — cases, documents, inbox, articles, appointments, availability,
      team, users — is always MSW: it lives in src/mocks/data.ts and resets on
      every page reload.

  (b) Naming. The app is JurisFlow in the code and in the UI; the repo was
      renamed from "LegalFlow". Only localStorage key names keep the legacy
      prefix (a one-time migration for an already-saved AI key).

  (c) "Frontend only". Every screen here is React + TypeScript running in the
      browser, and every /api/* call is answered by the MSW service worker, so
      there is no backend and no database. The repo does ship an OPTIONAL
      Express + MySQL auth service in server/: with VITE_AUTH_BACKEND=mysql the
      login and register routes are answered by it instead of the mock, while
      everything else stays mocked. Use VITE_AUTH_BACKEND=mock for a demo that
      is 100% frontend.

  (d) The one real request. https://openrouter.ai/api/v1/chat/completions is
      called straight from React with the key from .env (or the per-device key
      saved in Settings). Without a key, without free quota, or with JSON the
      parser rejects, levels 3 and 4 of section 3b keep the demo working and
      label the result as "msw" or "fallback".

  (e) FRESH INSTALL. The dataset starts EMPTY (src/mocks/data.ts): no cases,
      documents, inbox threads, articles, appointments or office hours, and one
      account only — the system administrator, who is also the single team row.
      Staff accounts come from the admin in Team Management: POST /api/team
      creates the directory card AND the sign-in account (default password
      password123, changeable in Settings), and deleting a member deletes both.
      Clients create their own account at /signup. Every create form therefore
      picks real people from the directory (/api/attorneys · /api/clients) or a
      real case, instead of a hard-coded demo name. A page reload returns to the
      empty state, because MSW keeps all of it in the page's memory.
