DATA MODEL (1 line per relationship; see docs/data-dictionary.md)
--------------------------------------------------------------------------------
  users 1---1 clients              (a client login owns one client file)
  clients 1---N cases              (matters)
  clients 1---N consultations      (intake requests)
  clients 1---N appointments       (bookings)
  clients 1---N documents          (uploads)
  users(lawyer) 1---N cases        (assigned_lawyer_id, the lead attorney)
  users(lawyer) 1---N appointments (the diary)
  users(lawyer) 1---7 availability (weekly grid, one row per day)
  cases 1---N documents            (case_id, optional)
  cases 1---N appointments         (via consultation_id)
  consultations 1---N appointments (a booking hangs off an approved request)
  documents 1---1 nlp_results      (newest analysis wins)
  users 1---N notifications        (the inbox)
  users 1---1 notification_settings
  users N---N permissions          (through role_permissions, per role)
  users 1---N activity_logs        (audit trail)
  legal_services 1---N consultations (practice area, ON DELETE SET NULL)

CONTRACTS
--------------------------------------------------------------------------------
  Service module  <->  blueprint        one file each, same names
  TypeScript type <->  table + view     types/index.ts mirrors the SQL columns
  ROLE_PERMISSIONS (TS)  ==  rbac.py  ==  seeders/002_role_permissions.sql
  Error contract:  { "error": string, "status": number } + the HTTP status

╚══════════════════════════════════════════════════════════════════════════╝

  The four steps requested in the brief, mapped to the real code path:

    BRIEF                        ACTUAL IMPLEMENTATION
    ─────────────────────────    ─────────────────────────────────────────────
    Step 1  User types problem   pages/user/GetSuggestionsPage.tsx textarea
    Step 2  POST /api/nlp/analyze analyzeLegalProblem() in
                                 src/ai/services/nlpService.ts — which tries
                                 OpenRouter FIRST, not MSW
    Step 3  MSW mocks or calls   MSW is the 3rd of 4 levels, not the entry

                                 when OpenRouter fails or is unavailable

  RESOLUTION ORDER (this is the important part — the brief has 2 and 3 swapped)

  ┌─────┬──────────────────────────────────────────────┬───────────────────┐

  The app ships EMPTY on purpose: the one `users` row is the system
  administrator (admin@firm.com / password123) and the one `teamMembers` row is
  the same person, so the firm directory has something to show. Every other
  collection starts empty and is filled from inside the app:

    staff           → Team Management (POST /api/team) creates the attorney /
                      secretary AND their sign-in account (default password
                      password123, changeable in Settings)
    clients         → self sign-up (POST /api/auth/register)
    cases           → the admin or secretary, with people picked from
                      GET /api/attorneys · GET /api/clients
    documents       → uploaded against one of those cases
    articles        → written by the admin in the knowledge base
    appointments    → booked against an attorney's published office hours
    availability    → published by each attorney

  A team member and a user account are two records for the same person, linked by
  EMAIL — that is what keeps them in step when the admin creates, renames or
  removes a member. MSW keeps everything in the page's memory, so a reload
  returns to this state.

     users ──1:N──▶ teamMembers       (role/status only — no user id)
     articles ──N:M──▶ cases          indirect: article.keywords match a query

  TWO THINGS THE ORIGINAL BRIEF GOT DIFFERENTLY
     • "cases to emails (1:N)"  → messages are keyed by users.userId, NOT by a
       case, so it is actually users ──1:N──▶ inboxMessages.
     • "users to articles (1:N)" → Article has no author id at all. It stores
       attorneySpecialist as a NAME string (a practice-area label such as
       'Patent Attorney'), so there is no FK from articles back to users.

  LIFETIME OF THE DATA
      page load ──▶ data.ts arrays are imported
                ──▶ each handler does  let casesData = [...cases]
                ──▶ your edits mutate THAT copy (visible until reload)
                ──▶ reload / F5 ──▶ back to the seed values in data.ts
      Nothing is written to disk, and nothing survives a refresh.

  6.3  WHERE THE BRIEF DIFFERS FROM THE CODE  (please read)

   (a) PROJECT NAME
       The brief says "LegalFlow". This project was renamed to JURISFLOW, and
       every string, package comment and test now says JurisFlow. The only
       remaining "legalflow" reference is a one-time localStorage migration key
       so an already-saved AI key is not lost on the rename.

   (b) AI MODEL
       The brief says  deepseek/deepseek-r1:free.
       That id is NOT usable: it is no longer offered as a free model by
       OpenRouter (verified against the live catalogue — 458 models, 21 free).
       An earlier PRIMARY, nex-agi/nex-n2.5-pro:free, is gone too, and the
       openrouter/free auto-router was deliberately removed from the chain
       because it could route to nvidia/nemotron-3.5-content-safety:free — a
       safety classifier that cannot produce legal JSON.
       The chain in 6.2 is what actually runs and what the accuracy tests cover.

   (c) "NO BACKEND / NO DATABASE"
       TRUE for app data (cases, documents, inbox, articles, appointments,
       availability, team) and for the AI path — see §1, §2 and §5.
       NOT TRUE for accounts. The repo also ships an OPTIONAL auth service:
            server/*.mjs            Node ESM + Express 5
            server/schema.sql       MySQL table `users`
            server/setup.mjs        npm run db:setup   (create + seed)
            server/index.mjs        npm run api        (listen on :4001)
       The `.env` file is NOT committed (it is gitignored; only `.env.example`
       is), so a fresh clone has no backend set and VITE_AUTH_BACKEND falls back
       to `mock`: login and sign-up are answered by MSW, and a registration
       lives only in that browser session. `server/setup.mjs` provisions the
       same single administrator the mock ships (admin@firm.com / password123).
            ▸ to persist accounts in MySQL:  VITE_AUTH_BACKEND=mysql  in .env,
              then npm run db:setup + npm run api. There, MSW's auth handlers
              are skipped, everything else stays mocked, and the MSW "who am I"
              helper falls back to the localStorage session so the §4 filtering
              keeps working.
            ▸ NOTE — the Team screen writes to the mock user store, so a member
              added there while the MySQL backend is active cannot sign in until
              the same row exists in the `users` table.
             ▸ db:setup only UPSERTS what it knows, so rows from an OLDER seed
               (john/michael/sarah@firm.com, clienta/clientb@email.com) survive,
               and `npm run db:setup -- reset` is the way to drop them: it
               re-creates the table with the administrator only, so client
               registrations go too.
